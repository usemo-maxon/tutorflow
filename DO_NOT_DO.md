# easy4tutor — чого не слід робити

Цей файл є негативною специфікацією. Якщо реалізація суперечить пунктам нижче, її не слід приймати без явного перегляду продуктового рішення.

## 1. Не розширювати MVP без потреби

Не додавати в першу версію:

- акаунти й кабінети учнів;
- повідомлення учням;
- прийом платежів від учнів через PayU;
- часткові оплати, передоплати, повернення та пакети уроків;
- PDF-звіти;
- бібліотеку готових навчальних планів;
- повноцінний файловий менеджер;
- двостороннє редагування подій через Google Calendar;
- темну тему;
- мобільний native-застосунок;
- AI-генерацію планів чи оцінок;
- маркетплейс викладачів.

Ці функції можливі пізніше, але не повинні затримувати основний цикл: учень → календар → урок → результат → оплата.

## 2. Не перетворювати продукт на generic dashboard

- Не починати головну з ряду однакових KPI-карток.
- Не використовувати фіолетово-синій gradient, glassmorphism, neon glow або абстрактні 3D-фігури як основну ідентичність.
- Не заповнювати екран декоративними ілюстраціями, які відсувають календар і наступний урок.
- Не використовувати однакові rounded cards для кожного фрагмента контенту.
- Не робити всі кнопки кольоровими й однаково гучними.
- Не використовувати круглі pill-кнопки всюди.
- Не додавати анімацію лише для «вау-ефекту».
- Не копіювати Google Calendar візуально; easy4tutor має власну педагогічну ієрархію.

## 3. Не ускладнювати створення уроку

- Не починати з порожньої довгої форми без вибраного учня.
- Не змушувати повторно вводити типову тривалість, формат і ціну.
- Не ховати календар під окремим кроком без видимості зайнятих слотів.
- Не створювати групу автоматично через накладання.
- Не дозволяти silent overlap.
- Не змішувати одиничний урок, набір дат і регулярну серію в один незрозумілий recurrence control.
- Не зберігати нескінченну recurring series без межі.
- Не закривати форму й не втрачати дані після server validation error.
- Не вимагати план уроку для самого факту бронювання, якщо викладач хоче заповнити його пізніше.

## 4. Не робити небезпечну синхронізацію

- Не вважати Google Calendar джерелом правди.
- Не дозволяти зміні в Google мовчки перезаписувати урок у easy4tutor.
- Не відновлювати видалену Google-подію без підтвердження.
- Не видаляти локальний урок лише тому, що Google API недоступний.
- Не блокувати створення уроку через тимчасову помилку Google.
- Не приховувати sync error після невдалої спроби.
- Не створювати дублікати під час retry; sync operations повинні бути ідемпотентними.
- Не робити OAuth або Google API-виклики з токенами напряму з браузера, якщо це відкриває секрети чи довгоживучі credentials.

## 5. Не плутати дані та статуси

- Не зберігати гроші як float.
- Не зберігати лише локальний час без timezone/UTC-контексту.
- Не рахувати оплату як поле всього групового уроку: вона належить кожному учаснику окремо.
- Не змішувати attendance і payment status.
- Не використовувати один boolean `completed` для статусів заплановано, потребує заповнення, заповнено та скасовано.
- Не копіювати спільний план групи в незалежні дублікати для кожного учня.
- Не видаляти історію уроків під час архівації учня.
- Не показувати архівованого учня в стандартному selector створення уроку.
- Не визначати фінансову статистику лише на клієнті з неповної сторінки результатів.

## 6. Не відкривати адміністратору приватні дані

- Не показувати адміністратору імена/контакти учнів, теми уроків, оцінки, нотатки, домашні завдання або вкладення.
- Не додавати «тимчасовий» impersonation без окремого security design, аудиту й законної підстави.
- Не використовувати admin role як універсальний bypass tenant isolation.
- Не логувати приватний контент у support dashboard.
- Не додавати PII в analytics, error tracking, URL, browser title або notification payload без необхідності.

## 7. Не покладатися на frontend як на захист

- Не вважати приховану кнопку авторизацією.
- Не довіряти `teacherId`, `role`, price, Founder status або payment result, отриманим лише від клієнта.
- Не перевіряти tenant ownership тільки в UI.
- Не зберігати access/refresh tokens у незахищеному localStorage без обґрунтованої архітектури.
- Не вкладати service secrets, PayU secret, Telegram bot token або Google client secret у frontend bundle.
- Не покладатися лише на client-side file validation.
- Не показувати raw stack traces, SQL errors чи provider responses користувачу.

## 8. Не підробляти стан оплати підписки

- Не активувати підписку лише через redirect із PayU.
- Не призначати Founder price під час реєстрації або старту trial.
- Не рахувати Founder slot на frontend.
- Не обіцяти місце Founder без успішної оплати й атомарного підтвердження backend.
- Не видаляти дані одразу після невдалої оплати підписки.
- Не блокувати експорт у read-only mode.
- Не приховувати дату наступного списання, період і реальну ціну.
- Не використовувати dark patterns для річного тарифу або скасування.

## 9. Не робити GDPR декоративним чекбоксом

- Не збирати дані «про всяк випадок».
- Не зберігати вкладення довше заявленого строку без законної причини.
- Не називати архівацію видаленням.
- Не обіцяти фізичне миттєве видалення з усіх backup, якщо система цього не гарантує.
- Не робити незворотне видалення одним випадковим кліком.
- Не дозволяти публічні постійні URL приватних вкладень.
- Не включати дані одного викладача в експорт іншого.
- Не створювати admin search по змісту приватних уроків.
- Не використовувати реальні дані учнів у development, demo, screenshots або automated tests.

## 10. Не нехтувати accessibility

- Не кодувати статус лише кольором.
- Не робити calendar доступним тільки через drag-and-drop.
- Не використовувати placeholder замість label.
- Не прибирати outline без рівноцінного focus indicator.
- Не робити клікабельні `div` замість button/link.
- Не відкривати dialog без focus trap і повернення focus.
- Не використовувати hover як єдиний спосіб побачити дію.
- Не зменшувати touch targets заради щільності.
- Не приховувати важливу інформацію від screen reader через візуальні трюки.

## 11. Не псувати mobile

- Не стискати desktop week calendar до ширини телефона.
- Не залишати широкі таблиці з горизонтальним scroll як єдиний mobile UX.
- Не перекривати контент floating-кнопкою або bottom navigation.
- Не ховати головну дію в меню з трьома крапками.
- Не вимагати точного drag gesture для перенесення уроку.
- Не відкривати side sheet шириною desktop на mobile; використовувати повноекранний flow.
- Не приховувати функції завершення уроку на телефоні.

## 12. Не створювати хаос у UI-копірайті

- Не змішувати польську, українську й англійську у видимому інтерфейсі.
- Не показувати enum/API-значення на кшталт `needs_completion`.
- Не використовувати технічні слова `rekord`, `payload`, `webhook`, `token bota` у звичайних сценаріях.
- Не називати ту саму дію `Zapisz`, `Dodaj`, `Utwórz` і `Potwierdź` у різних місцях без зміни змісту.
- Не писати vague errors: `Coś poszło nie tak` без пояснення й наступного кроку.
- Не використовувати гумор у помилках, оплатах, видаленні чи втраті синхронізації.
- Не вигадувати testimonials, customer logos, ratings або usage counters.

## 13. Не створювати frontend-антипатерни

- Не робити один гігантський component календаря/уроку на сотні рядків із усією логікою.
- Не дублювати бізнес-правила в кількох компонентах.
- Не змішувати API calls, validation, formatting і presentational markup без меж.
- Не використовувати глобальний store для кожного input.
- Не очищати весь query cache після кожної mutation.
- Не ігнорувати abort/cancellation пошукових запитів.
- Не використовувати array index як key для пунктів плану, учасників або occurrences.
- Не додавати залежність для функції, яку надійно виконує платформа кількома рядками.
- Не писати власний складний calendar/recurrence engine без вагомої причини; використовувати зрілу бібліотеку та покривати її адаптер тестами.
- Не змішувати display timezone з timezone recurrence rule.
- Не використовувати CSS magic numbers поза системою токенів.
- Не робити overrides через наростання specificity або `!important` як звичайну практику.

## 14. Не приховувати помилки та втрату даних

- Не показувати success до підтвердження критичної mutation сервером.
- Не скидати форму після network error.
- Не робити нескінченний spinner без timeout, error state або retry.
- Не замінювати весь екран generic error page через локальну помилку одного віджета.
- Не повторювати non-idempotent mutation автоматично.
- Не дозволяти подвійний submit створення уроку або checkout.
- Не закривати dialog до завершення критичної дії, якщо користувач потім не зможе зрозуміти її статус.
- Не мовчати про partial failure multi-date creation; бажано уникати його транзакційно.

## 15. Не оптимізувати без вимірювання

- Не віртуалізувати короткі списки.
- Не додавати складний offline-first sync у MVP.
- Не завантажувати календар, графіки й editor у initial bundle кожної сторінки.
- Не робити polling у кожному компоненті.
- Не передчасно кешувати permission/payment status так довго, що UI показує застарілий доступ.
- Не жертвувати коректністю timezone, recurrence або оплат заради «швидшого» коду.

## 16. Не приймати функцію без станів і тестів

Для кожної функції не можна обмежуватися happy path. До приймання мають бути визначені:

- loading;
- empty;
- success;
- validation error;
- server/network error;
- permission або read-only state;
- mobile behavior;
- keyboard behavior;
- аналітика без PII;
- unit/integration/E2E покриття відповідно до ризику.

Особливо не випускати без E2E-перевірки: створення уроку, серії, конфлікт/група, завершення уроку, Google sync retry, PayU confirmation, архівація/видалення та CSV export.

## 17. Stop-list перед merge

Не merge, якщо відповідь «так» хоча б на одне питання:

- Чи бачить admin приватні дані учня або уроку?
- Чи може retry створити дубль уроку або платежу?
- Чи можна втратити введений план через помилку мережі?
- Чи статус зрозумілий лише за кольором?
- Чи recurring action може змінити всю серію без явного scope?
- Чи PayU redirect сам активує підписку?
- Чи Google видалення автоматично змінює джерело правди?
- Чи frontend використовує float для PLN або локальний час без timezone?
- Чи critical flow неможливий із клавіатури або на mobile?
- Чи нова функція виходить за межі MVP без явного рішення?
